# Agent 统一通知 CLI 需求与设计文档

**版本**：v0.2（新增延迟通知，修订见第 8 节）  
**技术栈**：TypeScript (Node.js ≥ 20)  
**状态**：草案


## 1. 背景与目标

### 1.1 问题

本机同时使用 Claude Code、OpenCode、Pi 等多个 AI 编码 Agent。每个 Agent 都有各自的通知机制，但配置分散、凭据重复、维护成本高。用户希望在 Agent 任务结束或暂停时，通过 Bark 或 Telegram Bot 统一收到通知，且只需维护一套通知逻辑。

### 1.2 目标

开发一个 TypeScript CLI 工具（暂名 `agent-notify`），实现：

1. **统一通知渠道**：支持 Bark、Telegram Bot，凭据集中管理
2. **统一调用接口**：提供 `agent-notify --event <type>` 命令，所有 Agent 的 Hook/扩展均调用此命令
3. **自动探测与配置**：安装后通过 `agent-notify setup` 自动识别本机已安装的 Agent，交互式写入通知配置
4. **零运行时依赖**：安装后 CLI 即可用，不引入第三方运行时依赖，无需终端常驻
5. **可延迟通知**：任务结束/暂停后等待 N 秒再推送；期间任务恢复则自动取消（详见 3.5）

### 1.3 非目标

- 不替代各 Agent 自身的通知插件（如 Pi 的 `@herbertgao/pi-bark`）
- 不实现 MCP Server 或 Skill 形式的通知（Hook 是确定性触发，更适合此场景）
- v0.1 不覆盖所有 Agent，优先支持 Claude Code、OpenCode、Pi


## 2. 用户故事

| 编号 | 场景 | 预期行为 |
|---|---|---|
| US-1 | 用户全局安装 `agent-notify` 后执行 `agent-notify setup` | CLI 探测本机 Agent，列出检测结果，询问用户确认后写入配置 |
| US-2 | Claude Code 任务结束 | Hook 执行 `agent-notify --event stop`，Bark/TG 收到通知 |
| US-3 | OpenCode 等待权限确认 | Hook 执行 `agent-notify --event permission`，Bark/TG 收到通知 |
| US-4 | Pi 任务结束 | 扩展调用 `agent-notify --event settled`，Bark/TG 收到通知 |
| US-5 | 用户更换 Bark Device Key | 只改 `~/.config/agent-notify/config.json` 一处，所有 Agent 生效 |
| US-6 | 通知发送失败（网络问题） | CLI 静默退出（exit 0），不影响 Agent 正常运行 |


## 3. 功能需求

### 3.1 CLI 命令

```
agent-notify --event <type> [--message <text>] [--delay <秒>] [--session <id>] [--stdin-json]
agent-notify --cancel [--session <id>]     # 撤销该会话待发的延迟通知
agent-notify flush                        # 立即发送所有已到期的延迟通知
agent-notify setup [--dry-run] [--uninstall]
agent-notify test [--channel bark|telegram]
```

**`--event` 参数**：接收标准事件名，映射到不同通知文案。

| 事件名 | 触发场景 | 默认通知标题 |
|---|---|---|
| `stop` | Agent 任务正常结束 | 任务完成 |
| `notification` | Agent 需要用户输入/权限 | 等待处理 |
| `error` | Agent 运行出错 | 任务出错 |
| `settled` | Pi 最终稳定（兼容用） | 任务完成 |

**`setup` 子命令**：交互式探测和配置写入，详见 3.2。

**`test` 子命令**：发送测试通知，验证 Bark/TG 配置是否有效，并输出每个渠道的结果与耗时。

**`--stdin-json` 参数**：从 stdin 读取 Agent 传入的事件 JSON（Claude Code Hook 会提供 `session_id`、`cwd`、`hook_event_name` 等），用于填充 `--session` 与通知正文。读取最多等待 300ms，超时或解析失败则忽略，绝不阻塞。

### 3.2 自动探测与配置

#### 3.2.1 探测逻辑

| Agent | 探测信号 | 依据 |
|---|---|---|
| Claude Code | `~/.claude/settings.json` 存在，或 `~/.claude/` 目录存在 | Claude Code 用户级配置固定在此路径  |
| OpenCode | `opencode` 命令在 PATH 中，或 `~/.config/opencode/` 目录存在 | 插件配置目录位于 `~/.config/opencode/`  |
| Pi | `pi` 命令在 PATH 中，或 `~/.pi/` 目录存在 | Pi 包配置在 `~/.pi/agent/` 下  |

#### 3.2.2 配置写入策略

**Claude Code**：修改 `~/.claude/settings.json` 的 `hooks` 字段，写入：

```json
{
  "hooks": {
    "Stop": [{ "hooks": [{ "type": "command", "command": "agent-notify --event stop" }] }],
    "Notification": [{ "hooks": [{ "type": "command", "command": "agent-notify --event notification" }] }]
  }
}
```

Claude Code 的 Hook 事件包括 `Stop`（Agent 停止）和 `Notification`（发送通知时）。写入前保留已有 hooks，合并新条目。

**OpenCode**：OpenCode 的插件机制支持通过 `opencode.jsonc` 的 `plugins` 数组加载插件 。但为了统一 CLI 方案，v0.1 采用**生成一个极简 OpenCode 插件文件**的方式，放在 `~/.config/opencode/plugins/agent-notify.ts`，内容为监听 `session.idle` 和 `session.error` 事件并调用 `agent-notify`。

OpenCode 的 `session.idle` 对应 Agent 完成等待输入，`session.error` 对应会话出错 。该插件由 setup 自动生成，用户无需手动维护。

**Pi**：Pi 的扩展系统支持 TypeScript 模块，`agent_settled` 事件是“最终稳定、仅用于通知”的边界，正好对应任务完成场景 。setup 在 `~/.pi/agent/extensions/` 下生成一个极简扩展文件，监听 `agent_settled` 并调用 CLI。

如果 Pi 扩展生成失败（权限或版本问题），setup 输出提示：“Pi 需要手动安装通知扩展，或确认 `~/.pi/agent/extensions/` 可写。”

#### 3.2.3 交互流程

```
$ agent-notify setup

正在检测本机 Agent...

检测到以下 Agent：
  [1] Claude Code (~/.claude/settings.json)
  [2] OpenCode (命令: opencode)
  [3] Pi (命令: pi)

为哪些 Agent 配置 Bark/TG 通知？(默认全部，输入序号取消选择，回车确认): 

将执行以下修改：
  • Claude Code: 在 ~/.claude/settings.json 添加 Stop 和 Notification hooks
  • OpenCode: 创建 ~/.config/opencode/plugins/agent-notify.ts
  • Pi: 创建 ~/.pi/agent/extensions/agent-notify.ts

确认写入？(y/N): y

配置完成。
下一步：设置 Bark/TG 凭据
  • Bark: export BARK_DEVICE_KEY=your_key
  • 或编辑 ~/.config/agent-notify/config.json
```

**`--dry-run` 模式**：只输出将要修改的文件和内容，不实际写入。

**`--uninstall`**：移除本工具插入的 Hook/插件/扩展条目，保留用户自有配置。写入前先备份 `*.bak.<时间戳>`，用「临时文件 + rename」原子替换；若目标 JSON 解析失败则中止，不覆盖原文件；已存在相同命令时不重复追加（幂等）。

### 3.3 配置管理

配置文件路径：`~/.config/agent-notify/config.json`

```json
{
  "bark": {
    "enabled": true,
    "endpoint": "https://api.day.app/{device_key}",
    "deviceKey": "{env:BARK_DEVICE_KEY}",
    "group": "agent-notify"
  },
  "telegram": {
    "enabled": false,
    "botToken": "{env:TG_BOT_TOKEN}",
    "chatId": "{env:TG_CHAT_ID}"
  },
  "events": {
    "stop": { "bark": true, "telegram": true },
    "notification": { "bark": true, "telegram": true },
    "error": { "bark": true, "telegram": true }
  },
  "timeoutMs": 3000,
  "delayMs": {
    "stop": 180000,
    "settled": 180000,
    "error": 0,
    "notification": 0,
    "max": 300000
  },
  "aggregateWindowMs": 5000,
  "stateDir": "~/.config/agent-notify/state"
}
```

**凭据解析**：支持 `{env:VAR_NAME}` 占位符，在运行时替换为环境变量值。这样凭据可以放在 shell profile 或 `.env` 文件中，不硬编码在配置里。此模式参考了 OpenCode notification SDK 的变量替换设计 。

### 3.4 通知发送

CLI 读取配置后，根据 `--event` 参数选择文案，**并发**调用 Bark 和 Telegram API。任一渠道失败不影响其他渠道，所有失败均静默处理（仅写入本地日志 `~/.config/agent-notify/error.log`，不阻塞 Agent）。

**超时**：单次 HTTP 整体超时 3 秒（可配置）。但作为 Hook 调用时，**命令本身必须在 1 秒内返回**：延迟通知与网络发送都交给后台进程，主进程只写队列/发请求后立即 exit 0。

### 3.5 延迟通知（v0.2 新增）

**目标**：Agent 结束或暂停后不要立刻推送，等待用户配置的 N 秒再通知；期间任务恢复（用户继续输入、Agent 自动重试）则撤销该通知，避免“刚离开就响、回来又响”。

#### 3.5.1 参数与默认值

| 来源 | 说明 |
|---|---|
| `--delay <秒>` | 单次覆盖，`0` 表示不延迟 |
| `delayMs.<event>` | 每种事件的默认延迟；`stop`/`settled` 默认 300000（5 分钟），`error`/`notification` 默认 0 |
| `delayMs.max` | 上限（默认 600000，硬上限 1800000），超出则截断并写日志 |
| `aggregateWindowMs` | 到期聚合窗口，默认 5000 |

`notification` 事件（等待权限/输入）默认**不延迟**：用户需要立即看到才能继续。

#### 3.5.2 执行机制

1. `delay = 0`：与 v0.1 一致，当前进程内并发发送后退出。
2. `delay > 0`：只写一条待发记录，然后 `spawn(process.execPath, [cli, 'flush', '--session', id], { detached: true, stdio: 'ignore', windowsHide: true }).unref()`，主进程立即 exit 0。
3. 后台进程按 `dueAt` 睡眠，到点后原子认领（优先 `open(lock, 'wx')` 独占创建；跨平台语义比 `rename` 更可控）再发送，发送后删除记录。
4. `dueAt` 是绝对时间戳（事件发生时刻 + 延迟），所以机器休眠/唤醒后会立即发送已过期通知，而不是重新计时。

**队列记录**（`stateDir/pending/<session>.json`）：

```json
{
  "session": "abc123",
  "event": "stop",
  "title": "任务完成",
  "body": "pi · agent_notify_cli",
  "createdAt": 1729999970000,
  "dueAt": 1730000000000
}
```

#### 3.5.3 取消与去抖

| 触发 | 行为 |
|---|---|
| 同一 `--session` 再次收到事件 | 覆盖旧记录并重算 `dueAt`（只发最后一次） |
| `agent-notify --cancel --session <id>` | 删除待发记录，不发送 |
| 无 `--session` | 使用默认会话键（按 Agent 名），仍可去抖 |

Hook 集成：Claude Code 在 `UserPromptSubmit`、Pi 在 `agent_start`、OpenCode 在 `session.status`（busy）时调用 `--cancel`，即“任务恢复 → 撤销通知”。setup 默认写入该取消 Hook。

#### 3.5.4 聚合与可靠性

- **聚合**：flush 时把 `aggregateWindowMs` 内到期且事件类型相同的多条记录合并为一条（如“3 个任务已完成”），避免多 Agent 同时结束时连炸。
- **持久化**：队列写在磁盘；后台进程被系统杀死或重启后，任意一次后续 CLI 调用先扫一遍已过期记录并补发（`flush` 也可手动/定时调用）。
- **不重复**：发送前必须成功独占创建锁文件（`open(lock, 'wx')`）完成“认领”，创建失败说明已被其它进程处理，直接退出。
- **不丢不静默**：失败仍写 `error.log`（含事件与 session，不含凭据），退出码恒为 0。
- **取舍**：延迟期间机器关机/休眠且后台进程被杀，通知会在下次调用时补发（可能已过时）。这是“零常驻进程”的代价，v0.1 接受。


## 4. 非功能需求

| 需求 | 要求 |
|---|---|
| **启动速度** | CLI 冷启动 < 500ms（Node.js 脚本，无重型依赖） |
| **Hook 响应** | 作为 Hook 被调用时，命令必须在 1 秒内返回；延迟通知/网络发送均在后台进程完成 |
| **失败静默** | 任何通知发送失败，CLI 退出码为 0，不向 stderr 输出（除非 `--verbose`）；**禁止 exit 2**（Claude Code 中 2 表示阻止停止） |
| **配置安全** | 不硬编码凭据；支持环境变量引用；配置文件权限建议 `600`；日志脱敏（Bark key、TG token） |
| **兼容性** | Windows / macOS / Linux（Node ≥ 20）；Windows 为 v0.1 必选，而非后续 |
| **依赖** | 仅使用 Node.js 内置模块（`fs`、`path`、`os`、`child_process`、`util.parseArgs`、内置 `fetch`），零运行时依赖 |


## 5. 技术设计

### 5.1 项目结构

```
agent-notify/
├── package.json
├── tsconfig.json
├── src/
│   ├── cli.ts              # 入口，解析参数，分发命令
│   ├── config/
│   │   ├── loader.ts       # 读取/解析配置，处理 {env:} 占位符
│   │   └── schema.ts       # 配置类型定义（zod 或手写校验）
│   ├── notify/

│   │   ├── bark.ts         # Bark HTTP 发送
│   │   ├── telegram.ts     # Telegram Bot HTTP 发送

│   ├── util/

│   │   └── atomic.ts       # 备份/临时文件 + rename 原子写
│   ├── setup/
│   │   ├── detect.ts       # Agent 探测
│   │   ├── claude.ts       # Claude Code 配置写入
│   │   ├── opencode.ts     # OpenCode 插件生成
│   │   ├── pi.ts           # Pi 扩展生成
│   │   └── prompt.ts       # 交互式确认
│   └── templates/
│       ├── opencode-plugin.ts.tpl
│       └── pi-extension.ts.tpl
└── bin/
    └── agent-notify       # shebang + require('../dist/cli.js')
```

### 5.2 核心接口

```typescript
// 事件类型
type NotifyEvent = 'stop' | 'notification' | 'error' | 'settled';

// 渠道接口
interface NotifyChannel {
  name: string;
  send(title: string, body: string, config: ChannelConfig): Promise<void>;
}

// 配置
interface AgentNotifyConfig {
  bark?: BarkConfig;
  telegram?: TelegramConfig;
  events: Record<NotifyEvent, { bark: boolean; telegram: boolean }>;
  timeoutMs: number;
  delayMs: Record<NotifyEvent | 'max', number>;
  aggregateWindowMs: number;
  stateDir: string;
}

// 延迟队列记录（stateDir/pending/<session>.json）
interface PendingNotification {
  session: string;
  event: NotifyEvent;
  title: string;
  body: string;
  createdAt: number;
  dueAt: number;              // 绝对时间戳，非倒计时
}
```

### 5.3 依赖选择

| 用途 | 选择 | 理由 |
|---|---|---|
| CLI 参数解析 | Node.js `util.parseArgs` | 内置，且避免了全局安装多一个依赖；子命令少，手写分发很短 |
| 交互式确认 | Node.js `readline` | 只需 y/N 和序号选择，不值得引依赖 |
| HTTP 请求 | Node.js `fetch`（Node 18+ 内置） | 无需额外依赖，支持 `AbortSignal.timeout` |
| JSON 操作 | 原生 `JSON.parse/stringify` | 配置结构简单，无需额外库 |

**v0.1 依赖策略**：零运行时依赖，全部使用 Node.js 内置能力（`engines: node >= 20`）。原 v0.1 中“引 commander”与“零依赖”矛盾，v0.2 统一为零依赖。

### 5.4 安装方式

```bash
npm install -g @yourname/agent-notify
```

全局安装后，`agent-notify` 命令自动进入 PATH，任何 Agent 的 Hook 均可直接调用，无需终端常驻。Windows 下 npm 会生成 `agent-notify.cmd`，Hook 配置中直接写 `agent-notify` 由 shell 解析即可；扩展内 spawn 需 `{ shell: true }` 或指向 `.cmd`。


## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 用户已有 Agent 配置被覆盖 | 用户 Agent 无法正常工作 | 写入前备份 `*.bak.<ts>`；`--dry-run` 预览；交互式确认；解析失败则中止；`--uninstall` 可回退 |
| OpenCode/Pi 版本更新导致插件/扩展 API 变化 | 通知失效 | 生成的插件/扩展只做一件事：spawn detached 调用 CLI；API 面最小。新增 `agent-notify doctor` 验证 |
| 通知发送阻塞 Agent | Agent 响应变慢甚至会卡住停止流程 | Hook 模式下命令 1s 内返回；延迟与网络均在后台；不无界读 stdin（上限 300ms）；永远 exit 0 |
| 延迟通知丢失/重复 | 用户漏收或收到两次 | 队列持久化 + `dueAt` 绝对时间 + `rename` 原子认领；下次调用补发 |
| 延迟期间任务恢复 | 误报“完成” | `--cancel` + 同一 session 事件覆盖；setup 写入 `UserPromptSubmit`/`agent_start` 取消钩子 |
| 凭据泄露 | 安全风险 | 推荐环境变量方式；不将凭据写入 Hook 配置；日志脱敏 |
| Node 版本过低 | `fetch`/`parseArgs` 不可用 | `engines: >=20`，启动时检查版本并静默退出 |


## 7. 后续迭代（v0.3+）

- 增加 Aider、Cursor 等 Agent 的探测和配置
- 支持更多通知渠道（钉钉、飞书、Webhook）
- 提供 `agent-notify config` 命令，交互式编辑配置
- 支持 `--verbose` 输出调试信息
- 可选常驻调度器（`agent-notify daemon`），解决关机/休眠导致的延迟通知丢失


**附录：各 Agent 事件对照**

| Agent | 通知场景 | 对应事件/钩子 | 备注 |
|---|---|---|---|
| Claude Code | 任务结束 | `Stop` hook | 无 matcher；每轮回复结束都触发，需去抖/延迟 |
| Claude Code | 需要输入/权限 | `Notification` hook | 可用 matcher 区分 `permission_prompt` / `idle_prompt` |
| Claude Code | 撤销待发通知 | `UserPromptSubmit` hook | 仅 `--cancel`，不发通知 |
| OpenCode | 任务空闲 | `session.idle` | 事件 handler 为 fire-and-forget，不阻塞 |
| OpenCode | 出错 | `session.error` | 同上 |
| Pi | 最终稳定 | `agent_settled` | 唯一“不会自动继续”的通知点；`event.aborted` 可区分被打断 |
| Pi | 撤销待发通知 | `agent_start` | 仅 `--cancel` |

## 8. 本次评审修订说明（v0.1 → v0.2）

1. **新增 3.5 延迟通知**：`--delay`、`delayMs`、取消/去抖、聚合、持久化队列；延迟期间不阻塞 Agent（detach + 立即退出）。
2. **修正依赖矛盾**：去掉 `commander`，改用 `util.parseArgs`，真正零依赖（原 1.2 与 5.3 自相矛盾）。
3. **Hook 不能阻塞**：Claude Code 的 command hook 是同步的，且有 stdin 管道未关闭导致进程挂起的已知问题；新增 `--stdin-json` 的 300ms 上限与“Hook 模式 1s 返回”硬指标，明确禁止 exit 2。
4. **Windows 提前到 v0.1**：作者本机即 Windows；补 detached spawn、`windowsHide`、`.cmd` shim 说明。
5. **Claude Code Stop 语义**：`Stop` 是每轮回复结束而非任务完成；靠延迟 + 去抖降低噪声，或只勾选 `Notification`。
6. **配置写入安全**：备份、原子写、解析失败中止、幂等、`--uninstall`。
7. **通知正文**：建议带 Agent 名 + 项目目录名（hook JSON 的 `cwd`）+ 短 session id，多 Agent 并行时才分得清。
